# Phase 2: Rich text and vertical text Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Close audit rows "Rich text / HTML with field interpolation" (#4) and "Vertical text (tb-rl)" (#5), both behind. See `2026-10-04-arjs-parity-roadmap.md`, Phase 2.

**Architecture:**
- A new `richtext` report item. Its value is an HTML subset. A small tokenizer (`src/engine/text/rich.js`, no DOM, no `innerHTML`, no regex over user HTML) turns it into **blocks** (paragraphs, headings, list items) of **runs** (text + inline style).
- The rich layout breaks the runs into lines. A line holds **fragments**: a piece of text in one font, size, colour and decoration, at its own x. Mixed sizes on one line share one baseline.
- **Page model: one `text` item per fragment** (decision, see "Design decisions"). Each fragment is an ordinary `text` item with one line, so the PDF, SVG/viewer and HTML exporters draw it with no new code, shaped text included (`finishText` shapes per item). Underline and strike-through are `line` items, span backgrounds are `rect` items, `<a href>` becomes a `link` item over the fragment. The fragments carry `rich: {id, p, br?}` so text consumers (Word, Excel/CSV text dumps, `pw test` snapshots, viewer search) can put a line back together.
- Vertical text: `style.writingMode: 'tb-rl'` on a text box lays the text out in columns, right to left. CJK (and other upright) characters are stacked top to bottom as one `text` item per column; runs of Latin text are `text` items with Phase 1's `rotate: {a: 90, cx, cy}`, so every exporter already draws them.

**Tech Stack:** plain JS with JSDoc (`// @ts-check`), Vitest, pdf-lib, hand-written WordprocessingML, Next.js designer (React).

### Where the code differs from the plan, and why

1. **Security review 1 (DoS in the tokenizer).** `decode()` searched for the `;` of every `&` to the end of the input: O(n²). It now looks 10 characters ahead. Caps added after interpolation: 100,000 characters, 20,000 runs, 5,000 paragraphs, 5,000 `<br>`, 64 attributes per tag, 100 CSS declarations; `richValue` stops building once past the limit.
2. **Security review 2 (injection).** Data is escaped by default, quotes and `;` included (Design decision 2); `htmlFromData` opts in.
3. **Security review 3 (DoS in the layout).** The fragment cap was checked once per word: one long word in a narrow box made a line per character. `endLine()` stops at 5,000 lines / 20,000 fragments; spreads replaced by loops; sizes clamped to 1–400pt, line height 0.5–5, indent and spacing 0–144pt, list depth 10, no line taller than the page body.
4. **Security review 4 (URLs).** `src/engine/url.js` `safeUrl()` replaces the prefix regex in rich text *and* in `linkAction` (a bug already on main: `//host`, `/\host`, `https:host` passed). Used by url actions, rich links, PDF annotations, the HTML export and the viewer's `window.open`. Rich text no longer trims an href after checking it.
5. **List markers carry a space** (`"• "`), so text exports read "• item". Common named entities (`&mdash;`, `&hellip;`, quotes, `&copy;`, `&euro;` …) are decoded.
6. **Sup/sub in Word** use `<w:vertAlign>` at the line size (fragments carry `rich.s`/`rich.z`); block alignment rides on `rich.a`.
7. **FormattedText in a table cell** keeps only its words (a cell is plain text), with a warning.
8. **`check-pdf-matches-model`** checks only fragments that start a word and compares by prefix (pdftotext joins `bold` + `,` into one word); rotated items are skipped.

### Known limits after Phase 2

- Rich text is laid out left to right: fragments of a right-to-left paragraph are not reordered (each is still shaped). `text-align: justify` is treated as left. No tables, images, `font` tags, classes, margins or `line-height` CSS. Long words break by code point, not grapheme.
- A space keeps the style of the text before it is wrapped onto; an underlined word followed by a plain space draws the space plain.
- Word: links are plain text (no hyperlink relationship); span backgrounds are left out; vertical text becomes one paragraph per word.
- The designer canvas draws rich text at its designed height (no growth); the Preview tab grows it. `writingMode` shows in the inspector for rich text too but only text boxes use it.
- Vertical text: no bundled font has CJK glyphs (upload one); punctuation is not given vertical forms; no grow, split, decoration or justify; a Latin word longer than a column overflows it.

## Design decisions

1. **One text item per styled fragment, not per-run styles inside `lines[].runs`.** The roadmap suggested extending `lines[].runs` with `color`, `size` and `deco`. `runs` are already used by `finishText` for shaped / bidi text (made after layout, from one font and size per item). Giving runs their own size and colour would need changes in the PDF exporter (font per line, size per run), the SVG exporter, the HTML font subsetter, `fontKeysOf`, `finishText` and the PDF-vs-model check. A text item per fragment needs none of that: every exporter already draws text items exactly where the model says, so "PDF draws exactly what was measured" holds by construction. Cost: more items (one per style change, not per line) and consumers that read text as lines must join fragments; `textRows()` in `src/exporters/regions.js` does that once for all of them.
2. **Interpolation (changed after a security review).** Only the literal markup the author typed is HTML. Everything that comes from evaluation is escaped (`& < > " ' ;`): each `{…}` part of a template and the result of a value that is one `=expression`, so data can never add tags, links or styles, and a quote or `;` in a field cannot leave the attribute or CSS value it sits in (the CSS splitter treats `&#59;` as data). An item opts in to HTML stored in trusted data with `htmlFromData: true` ("Field values are HTML (trusted data only)"); then evaluated values are parsed too, through the same allow-list. The first draft parsed a whole `=expression` as markup; that let `=Fields.notes` inject links into generated PDFs (phishing). Documented in `docs/API.md`, "Rich text and data".
3. **Links.** `<a href>` keeps the same allow-list as `url` actions (`linkAction` in `src/engine/index.js`): `http:`, `https:`, `mailto:` or a path starting `/`, tested after entity decoding. Anything else (`javascript:`, `data:`, `vbscript:`) is dropped: the text stays, no link item is made, one warning.
4. **Limits (definitions are untrusted).** HTML longer than 100,000 characters is cut (warning). Tags nest at most 32 deep; deeper tags are ignored (their text is kept). Every loop is bounded by the input length; the tokenizer is a single forward scan with `indexOf`, no backtracking regex. At most 20,000 fragments per item.
5. **No hard-coded typography where the font knows better** (Phase 1 rule). Superscript and subscript size and offset come from the font's OS/2 table (`ySuperscriptYSize`, `ySuperscriptYOffset`, `ySubscriptYSize`, `ySubscriptYOffset`) through `TextMeasurer.script()`, with fallbacks for fonts that lack them. Heading sizes follow the browser defaults (2, 1.5, 1.17, 1, 0.83, 0.67 em, bold). List indent and paragraph spacing are item properties (`listIndent`, default 18 pt; `paragraphSpacing`, default 4 pt) in `RICH_DEFAULTS`.
6. **Vertical text fonts.** No bundled font covers CJK. The layout handles CJK code points (upright, one em per character), but they draw as boxes unless a font that has them is uploaded and used (the engine already warns "No font has these characters"). Tests use code-point geometry and Latin text.

describe('vertical text', () => {
  const vbox = (value, extra = {}) => report([{ type: 'textbox', name: 'V', x: 0, y: 0, w: 60, h: 100, value, style: { writingMode: 'tb-rl', fontSize: 10, padding: 0 }, ...extra }]);

    expect(glyphs.map(l => l.text).join('')).toBe('日本語のテキストです');
    expect(items.every(i => !i.rotate)).toBe(true);
    // first column: rightmost; y goes down
    expect(glyphs[1].y).toBeGreaterThan(glyphs[0].y);

  });
  it('wraps to a new column to the left when the column is full', async () => {
    const glyphs = (await out(vbox('一二三四五六七八九十一二三四五'))).pages[0].items.filter(i => i.t === 'text').flatMap(i => i.lines);
    const xs = [...new Set(glyphs.map(l => Math.round(l.x)))];
    expect(xs.length).toBe(2);
    expect(xs[1]).toBeLessThan(xs[0]);
  });

## Known limits (planned)

- Rich text is laid out left to right: a right-to-left paragraph's fragments are not reordered (each fragment is still shaped). `text-align: justify` in rich text is treated as left.
- No tables, images, `font` tags or CSS classes in rich text; `margin`, `padding` and `line-height` CSS are ignored.
- Vertical text: no upright/rotated punctuation forms (、。 are drawn upright as they come), no grow or page split, no CJK font bundled.
