# Phase 6: Viewer Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Close audit rows #29–#35 of `2026-10-04-arjs-parity-roadmap.md`, Phase 6: print, full screen and view modes; a mobile layout; a toolbar customisation API; UI languages (with RTL); frozen table headers; search options; parameter editors and a parameter grid.

**Architecture:**
- The viewer is one React component (`src/viewer/ReportViewer.jsx`), used by the viewer page, the designer's Preview tab, the embed (`src/embed/index.js`, inside a shadow root) and the interactive HTML export. Everything here lands in that component, so every host gets it.
- Logic that can be tested without a browser moves into one framework-free module, `src/viewer/logic.js`: search (`findText`), toolbar arrangement (`arrangeToolbar`), the galley definition (`galleyDefinition`) and the frozen-header lookup (`frozenAt`). Vitest covers it; Playwright covers the wiring.
- UI strings move to `src/i18n/` (one file per language, `index.js` with `t()`, `dirOf()`, `LANGUAGES`). `src/viewer/i18n.js` re-exports it so old imports keep working. A unit test checks that every language has every key and the same `{placeholders}`.
- Galley view reuses the engine's pageless renderer: the viewer renders a copy of the definition with `page.size = 'Pageless'` and the report's own page width. No engine change.
- Frozen headers need to know where each repeated table header sits on a page. Only the engine knows that, so the engine gets one small, additive change: each page may carry `frozen: [{x, y, w, h, end}]` (header rectangle and where the table ends on that page). Nothing else reads it; exporters ignore it.

**Tech Stack:** plain JS with JSDoc, React function components, Vitest, Playwright (e2e), Next.js 16.

**Design decisions taken without asking (simplest safe option):**
1. **Range and date-range parameters are multi-value parameters** holding two values (`"10,50"`). That is how the engine already passes lists (`Parameters.x` is an array, `Join()`, `in`). The designer turns `multi` on when one of these editors is picked; the viewer treats them as two values whatever `multi` says.
2. **Language is picked by `?lang=`** on every page (viewer, designer, home, admin, login) and the embed's `lang` option, as the viewer already did. Links from the home page keep the `lang`. No cookie: that is a new mechanism nobody asked for.
3. **RTL is set on the app's root element** (`dir="rtl"` on `.viewer`, `.designer`, the home shell), not on `<html>`: the root layout cannot see the query string, and the embed has no `<html>` of its own. Report pages and the designer canvas stay `dir="ltr"`: they are drawn at fixed coordinates.
4. **Translations are machine quality** (the roadmap wants a native-speaker review before shipping; the task owner accepted machine quality for now). Each language file says so at the top. The designer's Inspector, data dialogs and wizards stay English for now (fallback to `en` per key); the designer chrome, the parameter dialog, home, admin and login are translated.
5. **Frozen headers in continuous and galley views only** (single-page view shows one page; the header is on it). The overlay is the current page's SVG cropped to the header rectangle with a `viewBox`. Frozen first columns (roadmap row 33's second half) are not in this phase.
6. **Print** renders the same PDF as the PDF button (`pdfBlob`) into a hidden iframe appended to `document.body` (outside the embed's shadow root) and calls `print()` on it; if that throws (blocked, or a browser that will not print a PDF frame) it opens the PDF in a new tab.

```js
import en from './en.js'; import hi from './hi.js'; /* … es fr de ja zh pt-BR ar */
export const STRINGS = { en, hi, es, fr, de, ja, zh, 'pt-BR': ptBR, ar };
export const LANGUAGES = Object.keys(STRINGS);
const RTL = new Set(['ar']);
export const dirOf = (lang) => (RTL.has(pickLang(lang)) ? 'rtl' : 'ltr');
export function pickLang(v) {
  const s = String(v || '').trim();
  return LANGUAGES.find(l => l.toLowerCase() === s.toLowerCase()) || LANGUAGES.find(l => l === s.split('-')[0].toLowerCase()) || 'en';
}
export function t(lang, key, vars) {
  const s = (STRINGS[pickLang(lang)])[key] ?? STRINGS.en[key] ?? key;
  return vars ? s.replace(/\{(\w+)\}/g, (_, k) => String(vars[k] ?? '')) : s;
}
```

```js
/** Built-in toolbar items minus `hide`, plus custom `add` items placed after the item they name (else at the end). */
export function arrangeToolbar(builtIns, { hide = [], add = [] } = {}) {
  const hidden = new Set(hide);
  const out = builtIns.filter(i => !hidden.has(i.id));
  const taken = new Set(builtIns.map(i => i.id));
  for (const a of add) {
    if (!a || !a.id || taken.has(a.id)) continue;
    taken.add(a.id);
    const at = out.findIndex(i => i.id === a.after);
    const item = { ...a, custom: true, group: at >= 0 ? out[at].group : `custom:${a.id}` };
    if (at >= 0) out.splice(at + 1, 0, item); else out.push(item);
  }
  return out;
}
```

In `ReportViewer`, the toolbar becomes a list `[{ id, group, primary, node }]` passed through `arrangeToolbar(items, toolbar)`; consecutive items of one group render inside one `.tgroup`; each rendered element carries `data-toolbar-id`. A custom item renders `<button className="btn sm" data-toolbar-id={id} title={title} onClick={() => onClick(api)}>{label}</button>` where `api = { page, pages, goTo, run, print, exportAs }`. `mountViewer(el, { toolbar })` passes the prop through.

```js
export function galleyDefinition(def) {
  const pg = resolvePage(def.page);
```

### Where the code differs from the plan

1. **Parameter controls live in `src/viewer/ParamInput.jsx`**, not inline in ReportViewer, so a concurrent edit to the parameter panel (hidden/nullable parameters) merges cleanly.
2. **Search groups lines itself, following `textRows()`** (`src/exporters/regions.js`, from main): `textRows()` returns strings only, and search needs each line's box for the highlight, so `findText` in `logic.js` groups runs with the same rules (justified words by baseline joined with spaces; rich-text fragments by `rich.id`/`rich.l` joined with nothing).
3. **The paging buttons keep `title` only, no `aria-label`.** An `aria-label` with "page" in it made the smoke test's `getByLabel('Page')` ambiguous; the title still names them.
4. **The engine change is in `src/engine/index.js` `assemble()`**: 12 added lines, `pages[i].frozen = [{x, y, w, h, end}]`, only when a page has a table with a repeated header.
5. **Galley exports and print are of the paged report**: a galley view renders the paged report again for print/PDF/Excel/Word/HTML/CSV.
6. **The Rich text tool (from main) got its label in all nine languages.**

- The translations are machine quality. The roadmap wants a native speaker's review before shipping.

- Frozen headers cover the header row only, not frozen first columns. They work in continuous and galley view only.
- On a phone, the match-case and whole-word buttons appear only while the search box has focus.
- Print relies on the browser printing a PDF from a frame. Where that throws, the PDF opens in a new tab. A browser that silently prints a blank frame is not detected.
- The toolbar API hides and adds items. There is no "replace": hide an item and add your own after its neighbour.
- At 1280 px wide, the toolbar wraps to a second line while a search is active.
