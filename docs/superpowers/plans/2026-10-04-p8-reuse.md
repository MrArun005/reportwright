# Phase 8: Reuse and Authoring — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Close audit rows #42–#49 of `2026-10-04-arjs-parity-roadmap.md`, Phase 8: stylesheets and style inheritance, themes, master reports, report part libraries, layers, fixed-page overflow placeholders, a cell-based design mode, and the pivot wizard with instant visuals. Every feature is usable from the Designer alone.

**Architecture:**
- **One loader for everything reused.** A master, a part library, a stylesheet and a theme are all ordinary saved reports, referenced by report id. The engine reads them through `opts.loadReport`, the path subreports already use: the server renderer (`readReportFor`, so permissions apply), the browser and the worker (`/api/reports/:id`), the interactive HTML export (bundled reports) and the CLI (a sibling `<id>.pw.json`). No new storage kind and no server change. `src/engine/reuse.js` holds the resolution: a per-render cache (each id loaded once), at most **50 distinct reports per render** and **4 levels** of master or library nesting; a report that reaches itself (a master of itself, a library part that inserts itself) is reported as a warning and skipped, never followed. Resolution is linear in the number of references (memoised per id and per part), never per instance.
- **Masters (#44)** are merged into the content definition before validation (`applyMaster`). The master's page wins; its page header and footer items come first and the content's own items follow; data sources, data sets, parameters, functions, images, named styles and layers are a union (the content wins on a name clash). The content body is laid out inside the master's `placeholder` item: content coordinates are relative to the placeholder, wrapped in a container that does not keep together, so the content still grows, splits across pages and pushes the master items below it down. Without a placeholder the content goes under the master's body. A master may itself have a master (up to 4 levels).
- **Parts (#45)**: a library report lists `parts: [{ name, item, label, description, properties: [{ name, label, type, default }] }]`, where `item` names one item of the library. An instance is `{ type: 'part', library, part, properties: { … } }`: linked, so a change to the library shows in every report on the next render. At render time the instance becomes a copy of the library item at the instance's position, laid out with `PartProperties.<name>` (defaults, then the instance's values). Any item can carry `partProps` (the same values), which is what "Detach" and "Insert a copy" produce: an independent copy whose expressions still read `PartProperties`. A library's data sources, data sets, parameters and named styles that the host lacks are added at render (and by the designer when a part is inserted).
- **Layers (#46)**: `layers: [{ name, target: 'all' | 'screen' | 'print' | 'export' | 'design', visible, locked }]` and `item.layer`. `layoutItems` skips an item whose layer is hidden or not for this render's target (all nesting levels). The target is `opts.target`, else `state.target`, else `export`; the viewer renders with `screen`, prints with `print` and exports with `export` (a second render only when the report has layers or a master). `design` (ARJS `TargetDevice: None`) items show only in the designer. `locked` stops selection and dragging in the designer.
- **Stylesheets (#42)**: `styles.named[x].parent` (inheritance, a chain of at most 10, cycles cut) and `styles.sheet: '<report id>'`: that report's named styles (and default text) sit under the report's own. Flattened once per render, so `resolveStyle`'s identity cache still works.
- **Themes (#43)**: `themeDef: { colors: { Dark1, Light1, Dark2, Light2, Accent1–6, Hyperlink }, fonts: { major, minor: { family, size, weight, style } }, constants: { name: value } }` on any report (a "theme report" is a report with one). `theme: '<report id>'` or `theme: '=expression'` (evaluated with the parameters, so a parameter can pick the theme at run time); else the report's own `themeDef`; else a default (the Office palette). Expressions read `Theme.Colors.Accent1`, `Theme.Fonts.MajorFont.Family`, `Theme.Constants.Name`.
- **Overflow placeholders (#47)**: a table with `overflowTo: '<name>'` keeps its designed height (a fixed frame) and hands the rows that do not fit to the `overflow` item of that name, which fills its own frame on a later body section (the "next fixed page") with the table header repeated. An overflow item with its own `overflowTo` passes the rest on; the last one repeats its body section, page after page, until the rows run out (at most 500 repeats). On a repeated page the table itself is not drawn again.
- **Cell-based design (#48)**: a designer mode, stored as ordinary x/y/w/h. A grid of cells (size chosen in the canvas bar); positions and sizes snap to whole cells and a move, resize or insert that would overlap another item is refused. The engine does not change.
- **Pivot wizard and instant visuals (#49)**: a pivot wizard dialog (fields dragged — or clicked — into Rows, Columns and Values, a value's aggregate and "show as" % of total / row / column, a live preview) that inserts a Phase 4 tablix matrix. "Instant visuals": tick fields in the data panel and get a suggested chart, table and pivot drawn live with the sample rows; click one to insert it.

**ActiveReportsJS behaviour followed where the roadmap left a choice:**
1. Content report items are positioned relative to the master's content placeholder, and master items are read-only in the content report (ARJS `ContentPlaceHolder`). ARJS allows several named placeholders; we support one per master (the first), noted as a gap.
2. Report part properties are typed constants read in expressions (ARJS `PartProperties`); an instance stores the library and part name plus property values (ARJS `ReportPart: { Library, PartName, Properties }`), and is linked.
3. Layer targets follow ARJS `TargetDevice`: All, Screen, Paper (our `print`), Export, None (our `design`).
4. Theme colour and font names follow ARJS themes (Accent1–6, Dark1/2, Light1/2, Hyperlink, MajorFont, MinorFont, Constants). ARJS writes `Theme.Colors!Accent1`; our expression language uses `.`.

**Decisions** (besides the ActiveReports choices above):
1. Masters, libraries, stylesheets and themes are ordinary saved reports read through `loadReport` (no server change; the server's permission check applies). The CLI reads sibling `<id>.pw.json` files.
2. A content report's own page header and footer are replaced by the master's (the designer clears them when a master is picked). Data, parameters, styles: the content wins a name clash.
3. Layers filter in `layoutItems`, so they apply at every nesting level; the render target is `opts.target`, `state.target` or `export`.
4. The overflow frame is one unit (a fixed form does not split inside its frame).
