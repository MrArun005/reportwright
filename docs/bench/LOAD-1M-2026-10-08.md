# 1M-row streaming proof and server load: 8 Oct 2026 (partial)

Code: `main` @ 49c2934 (ReportWright 0.10.0). Raw results: `results-2026-10-08.jsonl` next to this file.

## The machine: not the cloud box the brief asked for

There was no cloud Linux host. The tests ran in a Linux container (`node:22-bookworm-slim`, Node 22.23.3, aarch64) under
Docker Desktop on an **Apple M2 MacBook Air with 8 GB of RAM** (4 performance and 4 efficiency cores).
- Container: `nproc` 8, `free -m` 3,918 MB total, no cgroup memory limit (the VM's 3.9 GB), and a CPU quota of 8 cores.
- The host disk had 4.5 GB free at the start.

**The run stopped part-way through test 2.** Under the server tests the Mac's swap filled (6.4 GB of 6.4 GB) and its free
disk fell to about 100 MB. The host then rebooted, and /tmp (the harness and its logs) was lost. The numbers below come
from the console output captured before the reboot. Tests 3 to 5 were not run, and they should not be run on this laptop.

## 1. Streaming CSV and XLSX at 1M rows: PASS (every run under 300 MB)

Method: `node scripts/mem-stream.mjs <csv|xlsx> 100000,300000,1000000 <plain|sorted|grouped>`. Each size runs in a fresh
process with `--max-old-space-size=192` (the small worker's heap). RSS is the whole render process, sampled every 10 ms.
The source is a lazy local HTTP JSON server.

| format | shape | 100k peak RSS | 300k | **1M peak RSS** | 1M above base | 1M time | 1M output |
|---|---|---:|---:|---:|---:|---:|---:|
| csv | plain | 167 MB | 176 | **178 MB** | +35 | 6.0 s | 50.4 MB |
| csv | sorted (spill) | 193 | 200 | **215 MB** | +72 | 9.8 s | 50.4 MB |
| csv | grouped | 206 | 205 | **211 MB** | +69 | 9.0 s | 50.4 MB |
| xlsx | plain | 185 | 189 | **183 MB** | +39 | 14.3 s | 34.4 MB |
| xlsx | sorted (spill) | 191 | 203 | **214 MB** | +63 | 18.2 s | 34.6 MB |
| xlsx | grouped | 197 | 199 | **207 MB** | +60 | 18.1 s | 36.3 MB |

Every shape is flat (its growth from 100k to 1M is under the harness's +30 MB limit). The real 1M figures (178–215 MB)
fall inside the research's projection of ~184–239 MB.

### Checking the files

The 1M grouped XLSX, a 1.1M plain XLSX and a 1M CSV were each written to disk with a copy of the harness that saves the stream
(peak 202, 189 and 175 MB).
- `unzip -t`: no errors in either XLSX.
- `xmllint --stream --noout` on every part: all well formed (sheet1 is 344 MB of XML). A DOM `xmllint` was OOM-killed on the
  344 MB sheet; that is xmllint's limit, not a defect in the file.
- 1M grouped: 1,000,016 `<row>`s (header, 7 group headers, 1M rows, 7 group footers, the grand total). The `SUBTOTAL` formulas
  hold the right ranges, and their cached values (qty 4,999,995, price 49,995,000) match LibreOffice's recalculation.
- **LibreOffice 26.8** (`soffice --convert-to csv`, all sheets) opened both files in 8–9 s. Its row counts: 1,000,016 for
  the grouped file; 1,048,576 + 51,427 for the 1.1M file.
- **The 1.1M sheet split works.** Sheet "Rows" has exactly 1,048,576 rows (a header and data ids 0..1,048,574). Sheet
  "Rows (2)" has the header again, ids 1,048,575..1,099,999 and the Total, so all 1,100,000 rows are there. That Total is a
  plain value (5,500,000), as docs/API.md says it should be.
- CSV: a BOM, a header and 1,000,000 data lines, CRLF line endings, no trailing newline.
- Minor: neither XLSX writes a `<dimension>`. That element is optional and Excel and LibreOffice open the files, but some
  readers use it to size the sheet.

## 2. Server PDF at scale (today's path, not streamed): partial

Production build (`npm run build`, 34 s), started with `next start`, `PW_AUTH=users`, SQLite storage, 16 service API keys
and `UV_THREADPOOL_SIZE=8`. The pool planned 7 workers, of which only **1 had a big heap** (1,024 MB), because the
container's memory is 3.9 GB. The request was `POST /api/v1/render` with `{template:'stress-scale', format:'pdf', parameters:{rows}}`.

| rows | status | time | PDF | pages | server RSS start → peak |
|---:|---:|---:|---:|---:|---:|
| 100,000 | 200 | 7.1 s | 4.4 MB | 2,175 | 787 → 1,058 MB |
| 200,000 | 200 | 10.3 s | 8.7 MB | 4,349 | 1,036 → 1,340 MB |
| 500,000 | not measured | | | | |
| 1,000,000 | not measured | | | | |

- `/api/sample/stress/<rows>` is capped at **200,000 rows** (`STRESS_MAX_ROWS`). That route cannot go past 200k.
- The attempt at 500k and 1M used an inline definition with a local data source. It returned 400 "Bad report id"
  because the harness put the definition under the wrong key. That is a harness mistake, not a product finding.
- The server's RSS after the 200k render stayed at 1.3 GB, against about 540 MB idle. On a 4 GB box that headroom
  ran out (see above).
- Expected from the research and the pool settings, not measured here: 500k and 1M exceed the 1 GB worker heap and
  end in "The render ran out of memory". At 1M, the JSON body (~110 MB) is also over `PW_FETCH_MAX_MB` (64), which
  gives 413.
